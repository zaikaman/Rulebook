# Codebase audit · 22 November 2026

Full read-through audit of Rulebook against the Reactive Omni Buildathon brief
(`hackathon-details.md`). Findings fixed after the audit ran have been removed; the
items below were re-checked against the current working tree (HEAD `0fa5971`).
Working tree was clean at `df0b79d` while the audit ran.

Scope: V2 contracts, shared encoding/recipe package, backend, frontend, deployment
records, documentation, and the repository gates. Judging weights considered:
Execution, Integration, Usefulness, Craft.

## Verdict

The code is in better shape than the submission materials around it. The contract
suite is coherent, the test count is real, CI is green, and every receipt published
in the README succeeds on-chain. What most threatens the entry is evidence drift:
the published smoke run was produced by a factory pair other than the recorded
current one, no deployed pair corresponds to `HEAD`, and the demo video is still
unlinked.

## A. Submission-blocking evidence problems

### A2. Smoke evidence belongs to a factory pair that is not the recorded current one

`docs/submission-evidence.md` and the README present the income-sweep smoke run on
Vault `0xBf52…` and Agent `0x9934…` as the headline proof. `deployments/workflows-v2-smoke.json`
records that run as created by agent factory `0x5a7c…` and vault factory `0xe09f…` at
commit `df0b79d`.

`deployments/workflows-v2.json` — the record the README points at for the current
pair — lists `0x3d7c…` (Reactive Lasna) and `0xe690…` (Unichain Sepolia) instead,
produced from `b239794`. The smoke factories appear nowhere else in the deployment
records.

So the strongest live evidence still demonstrates a build other than the advertised
one. The four README receipts themselves are genuine: `0xf968…`, `0x4608…`, `0x45a1…`,
`0x793f…` all return status 1. The problem is which factory the evidence attaches
to, not whether the transactions happened.

### A3. No deployed pair matches `HEAD`

`deployments/workflows-v2.json` records `commit: b239794` with `dirty: true` and
`source: working-tree` for both factories, so the deployed bytecode came from
uncommitted code. `HEAD` is now `0fa5971`, and `b239794` predates it.

The gap is not cosmetic: the agent deployed at `0x3d7c…` was built before `80c5d0d`,
which parked budget-blocked payment and transfer runs instead of consuming them. No
commit in the repository reproduces the running agent.

This remains the single hardest thing to explain in a submission: the deployed
system, the README, and `HEAD` are still three different states.

### A4. Demo video is missing

- `docs/submission-evidence.md` line 48 still says the video is "Not published yet",
  with no link anywhere.
- The hosted app URL is now linked in `README.md`, so only the video is outstanding.
- The brief requires a demo video under three minutes.

Missing artefact, not a code defect, but it caps the score regardless of code quality.

## C. Medium-severity behaviour and integration

### C2. Expired runs disappear without a signal

`WorkflowAgentV2.sol` line 390 returns on workflow expiry without requesting a
callback, so the run neither settles nor records a failure. Health cannot distinguish
"expired before execution" from "never seen", which is the sort of gap that shows up
in a live demo.

## D. Low-severity craft and polish

- **D1 Price-band copy.** `workflowFields.ts` lines 179-190 explain the reference price
  incompletely, and `WorkflowVaultV2.sol` line 449 resets the reference on refill while
  line 429 clears `eligibleAt` on skip. The semantics are defensible but not explained
  where the user chooses a band.
- **D2 Active-workflow cap.** `MAX_ACTIVE = 4` (`WorkflowAgentV2.sol` line 30) is
  enforced without a pre-submission warning; the fifth workflow fails after signing.
- **D3 Stale artefacts.** `backend/src/index.ts` lines 2-3 still carry a placeholder
  comment. `WorkflowAgentV2.sol` line 738 defines `_weekStart` and never uses it.

## G. Recommended fix order

1. Redeploy V2 from a committed tree and record the commit that produced it (A3).
2. Regenerate the smoke evidence against the advertised pair, or advertise the pair
   that produced it (A2).
3. Record and link the demo video (A4).
4. Surface expiry in health (C2).
5. Explain the price-band and reference-price semantics where the user chooses a band
   (D1).
6. Warn before the fourth active workflow is exceeded (D2).
7. Clear the remaining stale artefacts (D3).

## H. Limits of this audit

- No live UI walkthrough or wallet interaction was performed; the frontend was read,
  not driven.
- No load, adversarial, or fuzzing campaign beyond the existing test suite.
- Sponsor funding and Telegram delivery were reviewed in code, not exercised with
  live credentials.
- On-chain checks covered the factories, Vault linkage, `weeklyBudget` presence, and
  the four published receipts; other deployment claims were not re-derived.
- The contracts runs were made on Forge 1.9.0, and the tree has since been re-checked
  on that version; the snapshot gate passes locally.
