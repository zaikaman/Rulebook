# Codebase audit · 22 November 2026

Full read-through audit of Rulebook against the Reactive Omni Buildathon brief
(`hackathon-details.md`). Nothing in this document has been fixed; it is a findings
report only. Working tree was clean at `df0b79d` while the audit ran.

Scope: V2 contracts, shared encoding/recipe package, backend, frontend, deployment
records, documentation, and the repository gates. Judging weights considered:
Execution, Integration, Usefulness, Craft.

## Verdict

The code is in better shape than the submission materials around it. The contract
suite is coherent, the test count is real, CI is green, and every receipt published
in the README succeeds on-chain. What most threatens the entry is evidence drift:
the addresses the README calls "Current" are marked `superseded` in the deployment
records, the published smoke run belongs to an archived factory, no deployed pair
corresponds to `HEAD`, and the demo video and app URL are still unlinked.

One genuine logic bug can silently drop paid triggers, and should be fixed before
the code is frozen.

## A. Submission-blocking evidence problems

### A1. README advertises superseded factories as current

`README.md` lines 152-153 label the factory pair `0xce6f…` (Reactive Lasna) and
`0x6c5a…` (Unichain Sepolia) as "Current". Both are recorded as `superseded` in
`deployments/lasna.json` and `deployments/unichain-sepolia.json`, with the
superseding commit `09817e9`. The newest recorded pair is `0x4476…` / `0xc0ac…`.

A judge who follows the README to create a workflow can therefore land on a factory
the team itself retired, and every address they see afterwards will disagree with the
deployment records in the same repository.

### A2. Smoke evidence belongs to an archived factory

`docs/submission-evidence.md` and the README present the income-sweep smoke run on
Vault `0xC15a2BA79c63bd462f362867446E9a33731b814f` as the headline proof.

On-chain checks via public RPC (`cast`):

- `vaultOf(owner)` on the archived factory `0xc516…` returns `0xC15a…`, confirming the
  smoke Vault was created by that archived factory.
- The same lookup against `0x6c5a…` and against the newest `0xc0ac…` returns the zero
  address for the smoke owner.
- `0xC15a…` reverts on `weeklyBudget(bytes32)`, i.e. it predates the weekly budget
  feature, while a Vault created by `0x6c5a…` (`0xcf5d…`) returns budget data with
  `resetsAt = 1795392000`.

So the strongest live evidence in the submission demonstrates a build that is older
than the feature set being described, on a factory that is marked retired.

The four README receipts themselves are genuine: `0xf968…`, `0x4608…`, `0x45a1…`,
`0x793f…` all return status 1, and the newest Lasna factory runtime hash matches
`deployments/workflows-v2.json`. The problem is which factory the evidence attaches
to, not whether the transactions happened.

### A3. No deployed pair matches `HEAD`

The newest recorded deployment has `parentCommit = 1f17037`, which predates the
weekly-budget commits `6355ad4` and `7595b87`. More directly: the source at
`09817e9` for `WorkflowVaultV2.sol` contains no `weeklyBudget`, yet the Vault
deployed through factory `0x6c5a…` exposes it. The deployment was produced from
working-tree code that was never committed, so there is no commit a judge can read
that reproduces what is running.

This is the single hardest thing to explain in a submission: the deployed system,
the README, and `HEAD` are three different states.

### A4. Demo video and app URL are missing

- `docs/submission-evidence.md` lines 86 and 99 state that a video was recorded, with
  no link anywhere.
- `README.md` has no demo URL and no hosted app URL; the only link on line 19 points
  at a stale verification file.
- The brief requires a public repository, deployed addresses, transaction hashes, and
  a demo video under three minutes.

Missing artefact, not a code defect, but it caps the score regardless of code quality.

## B. High-severity logic and correctness

### B1. Budget rejection permanently consumes non-schedule triggers

`contracts/src/workflow/v2/WorkflowAgentV2.sol` lines 435-440:

```solidity
if (seen[runId]) return;
seen[runId] = true;
if (_budgetBlocks(workflow, run.observed)) return;
```

The comment explains the intent: avoid paying a callback fee for a run the Vault can
only reject, and leave the schedule in place so the next tick retries. That reasoning
holds for `SCHEDULE` triggers, which re-enter with a new `nextDue`. It does not hold
for `PAYMENT` and `TRANSFER` triggers, which are keyed on the origin transaction and
log index. Once `seen[runId]` is set, that exact event can never be processed again,
so a transfer that arrives while any leaf is budget-blocked is dropped forever even
after the week resets or the limits are raised.

`_budgetBlocks` (lines 498-529) is an any-leaf gate, so one blocked branch is enough
to discard the whole trigger.

Fix direction: keep `seen` for replay protection but only mark it when the run is
actually dispatched, or keep a separate `blocked` marker for triggers that are allowed
to retry. Do not change the schedule path.

### B2. Coverage gate only measures V1

`scripts/coverage-gate.mjs` lines 8-19 lists five V1 contracts and passes
`--skip Workflow`, so the V2 workflow contracts — the actual product — are outside
the gate. `contracts/.coverage-summary.json` is likewise V1-only, and its committed
numbers do not reproduce locally:

| Contract       | Committed | Local  |
| -------------- | --------- | ------ |
| `Vault.sol`    | 91.3%     | 86.75% |
| `VaultFactory` | 100%      | 77.78% |

The `verify` pipeline therefore reports coverage success while the shipped contracts
are unmeasured, and the committed snapshot overstates the current tree.

### B3. Zero cap is documented as unlimited but enforced as zero

`packages/shared/src/workflowFields.ts` line 360 tells the user:

> Optional. Blank or 0 means no per-run cap.

`contracts/src/workflow/v2/WorkflowProgramV2.sol` lines 232-235 rejects any spend above
`usdcCap` / `wethCap`, so a stored cap of zero blocks every spend. `workflowV2Draft.ts`
lines 320-321 convert a blank cap to `0`, which is exactly the case the hint describes
as unlimited. A user who leaves the field empty to mean "no limit" gets a workflow that
never pays out, and the UI told them that was correct.

Either treat zero as unlimited in the contract, or make the field required and rewrite
the hint. The contract behaviour is the safer of the two; the hint is the bug.

### B4. Large-transfer recipe produces an incomplete workflow

`packages/shared/src/workflowV2Recipes.ts` lines 284-291 build the large-transfer
recipe with an empty `subject`, so the workflow has no human-readable target and
copies badly. Related: `frontend/src/workflows/listingV2.ts` line 121 has
`copyListingDraft` clear `subject`, `usdcCap`, `wethCap`, and `expires`, so a user who
duplicates a listing silently loses its limits and description. Duplication is the
natural way to build a second workflow, and it produces a materially different one
without warning.

## C. Medium-severity behaviour and integration

### C1. Grace period reported as callback pending

`IN_GRACE_PERIOD` is a terminal-ish state, but three layers classify it as still
pending:

- `packages/shared/src/workflowHealth.ts` line 285
- `backend/db/migrations/0019_workflow_health.sql` lines 35-39
- the frontend inherits the backend classification

A judge watching a workflow sit in "pending" indefinitely reads that as a stuck
system. Grace should be its own displayed state.

### C2. Expired runs disappear without a signal

`WorkflowAgentV2.sol` line 358 returns on expiry without requesting a callback, so the
run neither settles nor records a failure. Health cannot distinguish "expired before
execution" from "never seen", which is the sort of gap that shows up in a live demo.

### C3. Gas assertion fails on a newer Foundry

`contracts/test/integration/Workflows.t.sol` line 176 asserts gas `< 800_000`. On the
locally installed Forge 1.9.0 the measured value is 853,949, so the suite reports
302 passed / 1 failed. CI pins `FOUNDRY_VERSION: v1.7.1` (`.github/workflows/ci.yml`
line 12) and passes.

The test is still brittle: a judge or a future maintainer running a current Foundry
sees a red suite on a green repository. Either raise the bound with headroom or
measure against a version-pinned reference.

### C4. Sponsor status invents healthy balances

`backend/src/api/routes/sponsor.ts` lines 31-39, when no sponsor source is configured,
return `state: 'healthy'` with zero reserves. `backend/src/sponsor/status.ts` lines
62-71 explicitly documents that fields should be omitted rather than invented. The
fallback contradicts the module's own contract and would show a healthy account that
cannot pay for anything.

### C5. V1 ABI used for V2 agents

`backend/src/sponsor/accountChain.ts` lines 20-28 call the V1 `getVault` signature
against V2 agents. It happens to work where the selector matches, but it couples the
backend to an ABI the V2 contracts do not promise, and it will break on the first
interface change.

### C6. Frontend environment drift

- `frontend/.env.example` omits `VITE_WORKFLOW_V2_DEPLOYMENT`,
  `VITE_WORKFLOW_V2_ACTIVATION`, and `VITE_LEGACY_WORKSPACE`, so a fresh clone cannot
  discover the V2 configuration from the documented source.
- `frontend/.env.local` points at the superseded `0xce6f…` / `0x6c5a…` pair with
  activation on and legacy off.
- `frontend/src/workflows/chainV2.ts` lines 45-56 treat a missing deployment as
  `undefined` and force activation false, so a misconfigured build degrades silently
  instead of failing visibly.

## D. Low-severity craft and polish

- **D1 Price-band copy.** `workflowFields.ts` lines 179-190 explain the reference price
  incompletely, and `WorkflowVaultV2.sol` line 449 resets the reference on refill while
  line 429 clears `eligibleAt` on skip. The semantics are defensible but not explained
  where the user chooses a band.
- **D2 Active-workflow cap.** `MAX_ACTIVE = 4` (`WorkflowAgentV2.sol` line 30) is
  enforced without a pre-submission warning; the fifth workflow fails after signing.
- **D3 Stale artefacts.** `deployments/workflows-v2-verification.json` is dated 20
  November, lists factories `0xc0dd…` / `0xc516…`, and claims 286 tests.
  `backend/src/index.ts` lines 2-3 still carry a placeholder comment.
  `WorkflowAgentV2.sol` line 567 defines `_weekStart` and never uses it.
- **D4 Bundle size.** Main frontend chunk is roughly 1.34 MB, 406 kB gzip. Acceptable
  for a testnet demo, not for a first-load impression on slow links.
- **D5 Declared debt.** `docs/submission-evidence.md` line 75 admits lint is open with
  389 warnings. Listing known warnings is honest, but shipping them is a craft signal
  in the wrong direction.

## E. What is solid

Worth stating plainly, because the report above is necessarily negative:

- Contract structure is clean: factory, vault, agent, validator and protocol registry
  are separated, and the settlement interface is narrow.
- V2 test coverage is broad (302 passing tests) and the integration scenarios exercise
  real branch paths, scheduled runs, and destination callbacks.
- CI #52 on `df0b79d` succeeded; Deploy production #23 succeeded.
- All four published README receipts confirm on-chain success, and the newest Lasna
  factory runtime hash matches its deployment record.
- Shared validation, recipes, and draft conversion are single-sourced rather than
  duplicated between frontend and backend.
- Formatting, typecheck, lint, design-system check, and production build all pass
  locally.

## G. Recommended fix order

1. Redeploy V2 from a committed tree and record the commit that produced it.
2. Replace the advertised factory pair and regenerate smoke evidence against the new
   pair; re-run the income-sweep demo so the evidence matches the advertised build.
3. Fix B1 (trigger consumption before the budget gate) before freezing code.
4. Correct the cap hint and the zero-cap draft conversion (B3).
5. Complete the large-transfer recipe and decide whether duplication should drop
   limits (B4).
6. Add V2 contracts to the coverage gate and regenerate the committed snapshot (B2).
7. Separate grace from pending in health, and surface expiry (C1, C2).
8. Record and link the demo video, publish the app URL, and update the README links
   (A4, D3).
9. Address C4, C5, C6 and the low-severity craft items as time allows.

## H. Limits of this audit

- No live UI walkthrough or wallet interaction was performed; the frontend was read,
  not driven.
- No load, adversarial, or fuzzing campaign beyond the existing test suite.
- Sponsor funding and Telegram delivery were reviewed in code, not exercised with
  live credentials.
- On-chain checks covered the factories, Vault linkage, `weeklyBudget` presence, and
  the four published receipts; other deployment claims were not re-derived.
- The exact CI toolchain was not reproduced locally because installing Foundry v1.7.1
  alongside the installed 1.9.0 was out of scope for an audit-only pass.
