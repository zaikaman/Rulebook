# Rulebook audit against the Reactive Omni Buildathon brief

Date: 2026-11-25
Scope: entire repository (V2 contracts, shared package, backend, frontend, deployment records, submission docs) reviewed against `hackathon-details.md`.
Mode: read-only. No source, test, config, or deployment file was modified.

## Verdict

The contracts are in good shape and the local test matrix is green, but the submission is currently undermined by one structural problem: the live app, the deployment record, and every published receipt point at different things. A reviewer following the README's "start with the receipts" path lands on a factory that never created those contracts, and the hosted app cannot display any run. That is the main risk to the Execution and Integration scores, not a code defect.

## What is genuinely solid

- `npm run typecheck`: exit 0.
- Unit tests: shared 27, frontend 53, backend 45, all pass.
- Foundry: `forge build` exit 0; `forge test` 79 passed, 0 failed.
- Playwright: 59 passed (2.4 min), including builder branches, invalid-drop rejection, and activation resuming after a declined signature.
- Contract design is sound: replay protection by `runId`, budget mirror never over-states, `InsufficientVaultBalance` recorded as skipped, bounded pending queue, expiry retirement, weekly reset verified in tests, assistant tools scoped to the session owner, and assistant/Rulewright/Telegram availability all true on the hosted backend.
- Hosted app returns 200 and embeds the current factory pair; backend `/health` is green with reachable RPCs and an enabled indexer.

## Critical detail

### C1. The receipts and the current deployment are disconnected

On-chain checks:

- Smoke Agent `0x6bF114…` has `factory() = 0xc64e9ecf…`; current Lasna factory is `0x69033914…`. `agentOf(0xC2500C19…)` on the current factory is `0x0`.
- Smoke Vault `0x95855cd0…` belongs to vault factory `0xc31c84d4…`; current Unichain factory `0xd34f11f6…` returns `vaultOf(0xC2500C19…) = 0x0`.
- Both current deployment transactions are real and successful: Lasna `0x4bbfe74a…` at block 9145016, Unichain `0xef3d865d…` at block 68679521, matching `deployments/workflows-v2.json`.
- The deployed bytecode matches HEAD: rebuilding the HEAD artifact and re-encoding the constructor args reproduces `creationInputHash 0xdb25dd3b…`, and the live implementation exposes the HEAD-only selectors (`resumeWatching`, `watchingPaused`, `wakeBlock`, `pendingRuns`).

So the contracts are not stale; the evidence is. `deployments/workflows-v2-smoke.json` also records `deploymentCommit: a464a05`, older than both `e8026cc` and HEAD `4278e13`.

Consequence: the README line 156 claim, "The receipts at the top of this file were produced by the current record," is false. A reviewer who opens the "Current factory pair" record and then the receipt Agent sees two unrelated deployments, which reads as a documentation error at best and fabricated evidence at worst.

### C2. Demo video missing

`hackathon-details.md` line 46 requires a demo video under three minutes. `docs/submission-evidence.md` line 48 still says "Not published yet." This is a submission blocker independent of the code.

### C3. The published runs are not viewable in the product

The hosted backend reads only the current deployment (start blocks 9145016 / 68679521):

- `/v3/health?owner=0xC250…` returns `{"workflows":[]}`.
- `/v3/activity` and `/v3/marketplace` return empty.
- `/v3/runs/0x6903b281…` and `/v3/runs/0x3da3cf97…` return 404 "This run has not been indexed."

The Public proof page is correctly wallet-free and reads callbacks from the Lasna system contract, but it needs a run id that the indexer produces. The demo cannot reproduce the published receipts in the app without a fresh run on the current pair.

## High detail

### H1. Builder accepts programs the validator rejects, with a poor error

`toProgram` (`packages/shared/src/workflowV2Draft.ts:431`) converts the draft without mirroring the on-chain constraints in `WorkflowProgramV2._actions` (`contracts/src/workflow/v2/WorkflowProgramV2.sol:202-219`):

- `BUY`/`SELL` with blank slippage: the field is `optional` with no minimum (`packages/shared/src/workflowFields.ts:385`), so it becomes `0`; the contract rejects at line 206. The hint says "At least 0.01%" but nothing enforces it.
- More than one swap on a single path: the contract allows only one (`swap` flag); the canvas does not prevent a BUY and a SELL on the same branch.
- `REFILL` not under a `USDC_BELOW` check: rejected at line 216.
- `INACTIVITY_PAYOUT` combined with another action, without `once`, or outside an `INACTIVITY` branch: rejected at lines 218-219.
- `PAYMENT_FROM` on a non-PAYMENT trigger or with an empty subject: rejected at lines 164-166.
- Percent-unit action on a non-PAYMENT trigger: rejected at line 202.

These are caught before any signature (`prepare()` and `activate()` both call `validateV2Program`), so this is not a fund-safety issue. It is a reviewer-experience issue: the first custom workflow someone tries can fail with "The contract function 'validateProgram' reverted with the following signature:" because `BuilderV2.tsx:1012` keeps only the first line of viem's message. The review/activation flow should either prevent the combination or translate `InvalidProgram` into the specific rule.

### H2. Second payment workflow

`WorkflowVaultV2.sol:236-239` permits only one PAYMENT-trigger workflow per Vault and reverts with the generic `InvalidAuthorization()`. Nothing in `frontend/src` or `packages/shared/src` reads `paymentWorkflow`, so the builder lets a user create and sign a second income sweep; the failure appears on the `authorizeWithWeeklyBudget` transaction (`frontend/src/workflows/chainV2.ts:664`). An income sweep plus a scheduled buy is fine; two payment programs are the broken case.

## Medium detail

### M1. Stale record metadata

`deployments/workflows-v2.json` says `commit: e8026cc`, `dirty: true`, `source: working-tree`. The deployed runtime matches HEAD `4278e13` (clean), and `e8026cc` predates the pause/resume contract changes. The bytecode hashes are correct; the metadata is not. This directly weakens the "someone else can follow and reproduce" criterion.

### M2. Stale docs

`docs/submission-evidence.md:35-37` claims 68 Foundry, 34 backend, 45 frontend tests; actual is 79, 45, 53. The 59 Playwright figure is correct. `docs/audit-2026-11-22.md` still lists A2/A4 as open, which is accurate for A4 but not for the bytecode question.

### M3. Empty marketplace

Zero published listings. The Marketplace and "copy as draft" flow are implemented and tested, but a reviewer sees "Nothing published yet." Publishing the demo workflow would make that page self-explanatory.

### M4. Indexer scan

`backend/src/workflows/indexerV2.ts:108` calls `getLogs` without an address for the destination scan and filters by event signature instead. At demo volume it is fine; at scale it will be the first thing to hit RPC limits.

## Low detail

### L1. Error truncation

`BuilderV2.tsx:1012` (`message.split('\n')[0]`) discards viem's actual reason. This compounds H1.

### L2. Dead V1 client

`frontend/src/lib/api.ts:152,160,203` still calls `/v1/chains`, `/v1/executions`, and V1 Telegram paths that the current backend does not register. No live UI path appears to call them, but they are a trap for anyone extending the app.

### L3. Misleading chain config

`packages/shared/src/chains.ts:43-46` gives the Lasna entry the Unichain router, USDC, WETH, and pair addresses. Lasna code does not use them today, but the "only place a chain address may appear" config now contains wrong data.

## Mapping to the judging criteria

- Execution: strong contract behavior, green tests, real receipts; damaged by C1/C3 because the receipts are not connected to the live product.
- Integration: the reactive contract does real work (subscriptions, price memory, branching, pending queue, budget mirror); the demo does not show it on the current pair.
- Usefulness: the product surface is coherent and the assistant is genuinely useful; an empty Marketplace and empty Activity weaken the first impression.
- Craft: clean separation and good comments; stale deployment metadata, stale test counts, and raw revert text are the visible cracks.
